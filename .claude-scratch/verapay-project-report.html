Overview

Verapay is a payment-operations portal — one codebase serving both the customer who moves their own money and the staff who watch the platform move everyone's.

Customers get a wallet, deposits, withdrawals, a unified transaction history, KYC document upload, an "Identity Vault" for their business and settlement details, support chat, and notifications. Admins and operators get a parallel console: a customer directory with suspend/reactivate controls, a KYC review queue, a treasury ledger showing running balance across every merchant, payment-gateway configuration, a support inbox, and an audit log of every sensitive action taken on the platform.

It's built deliberately small: vanilla PHP with PDO (no framework, no ORM, no Composer dependencies), MySQL for storage, Tailwind CSS compiled ahead of time so nothing fetches a build tool at runtime, and plain fetch() JavaScript per page instead of a frontend framework. Docker exists only to make local development painless — production is "point a document root at /public on ordinary PHP hosting."

Architecture at a glance

/public

The only web-accessible folder. Front controller (index.php) routes by URL path, plus every JSON API endpoint and all compiled CSS/JS/icons.

/pages

View templates — one file per screen. Included by the router, never reachable directly.

/includes

Shared PHP: auth/session/CSRF middleware, layout partials (sidebar, navbar, hero banner), money math, small helpers.

/config & /database

Environment loading and DB connection (outside the document root), plus schema and demo-data seed.

Every page and every API endpoint opens with require_auth(), which re-queries the caller's live account status from the database on that request. There's no session-token table to separately revoke — an admin suspending a customer takes effect on that customer's very next click, not their next login.

01 · UI

A full visual elevation pass, every module

30 files · 10 batches

The design system was already solid — brand tokens, a gradient hero banner, cards, badges. The gap was consistency and polish: plain tables with no visual hierarchy, three real bugs, and one page that had silently lost its hero banner.

  • New shared components added to the CSS layer: .icon-chip, .avatar-chip, .empty-state, .tab-btn, .progress-fill, .list-date-heading — so every page draws from one vocabulary instead of one-off markup.
  • Every data table — transactions, admin customers, audit log, treasury — gained per-row type icons, a colored left border keyed to status, and a real empty state with an icon and a next step, replacing plain "no results" text.
  • Three defects fixed: a duplicated "Mark all as read" button with a colliding id on Notifications; a gender field on Profile that was structurally nested inside the email field's wrapper; and Payment Gateways using a stray off-token purple instead of the shared brand-muted color, with its tabs rebuilt as a real segmented control.
  • Settings was the only signed-in page missing the hero banner — it now has one. KYC Verification gained a "3 of 7 uploaded" progress bar. Identity Vault's plain text rows became icon-labeled tiles.
  • Notifications now group by Today / Yesterday / This week / Earlier, each type tinted by tone (a deposit reads green, a security event reads violet).
verification: Playwright sweep, both roles, all 16 routes — 0 console errors, 0 PHP warnings, tab-switching and empty-state filtering confirmed live
02 · IDENTITY

Real, gender-matched profile photos

12 files · 3 API endpoints extended

Every avatar in the app — initials circles and line-icon silhouettes — became a real photo, matched to the account's gender where it's on file, and deterministically assigned (never random on reload) where it isn't.

  • Source: randomuser.me's stable portrait endpoints, requested live per page view — a deliberate trade-off the user chose over bundling static images, in exchange for a live third-party request per avatar render.
  • Deterministic, not random: the photo index is derived from the user's own database id, so the same person shows the same face every time, across every screen.
  • Everyone gets one — including accounts with no gender on file, which now get a stable (if unconfirmed) assignment rather than falling back to plain initials.
  • Graceful degradation: if the external photo fails to load, an inline onerror swaps in the original initials circle — never a broken-image icon.
  • Reach: navbar, hero banner, the Profile page, the admin Customers table, KYC review, and — added last — the support inbox's conversation list and message bubbles on both the customer and admin side.
verification: gender-matched URLs confirmed per account — 0 failed image requests, 0 console errors across the same full sweep

Data & security model

Storage

  • users — role (customer / operator / admin), status (active / suspended)
  • wallets — one per user, DECIMAL(18,2) balances, never float
  • transactions — one unified deposit/withdrawal ledger
  • business_profiles — KYC + settlement bank; document and account numbers stored as one-way hashes, last 4 digits only
  • payment_gateways — API keys stored the same way: hash + last 4 characters
  • support_conversations / _messages, notifications, audit_logs, login_attempts

Session & request security

  • Native PHP sessions, regenerated on login; HttpOnly, SameSite=Lax, Secure over HTTPS
  • CSRF token verified on every mutating request via X-CSRF-Token
  • All queries through PDO prepared statements, real server-side prepares
  • IDOR checks on support messages and notifications — ownership verified before any read or write
  • Per email+IP rate limiting on login, with a rolling lockout window
